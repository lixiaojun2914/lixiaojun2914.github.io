# 技术博客写作指南

- **文章主线**：开头交代本文的问题和范围，用“本篇文章介绍……”等自然措辞。正文按现象、实验、系统调用与源码、设计解释推进；不写成命令大全，也不把协作过程写成作者亲历。
- **标题层级**：正文标题一律编号。文章总标题由 Hugo 渲染为 H1，保留系列篇号；正文从 H2 开始，用 `一、`、`二、`、`三、`；H3 用 `2.1`、`2.2`，首位数字对应父章节；H4 用 `2.1.1`，更深层级依此类推。保留正确的 Markdown 标题级别，不跳级；代码块内的注释不参与编号。
- **实验和源码**：Bash 用于准备环境、编译与运行；需要控制文件描述符、偏移或调用顺序时用 C。注明实测环境和对应的源码版本；把 C 接口、跟踪输出和内核函数分开讲。例如 `read(3, "A", 1) = 1` 中的 `"A"` 是 strace 展示的读取结果，代码实际传入可写缓冲区的地址。
- **图表**：结果对照用 Markdown 表格；对象关系、调用链和状态变化用文章目录内的 SVG，并提供替代文本和正文说明。需要让读者操作或比较状态时，可用可访问的 HTML 演示，并为不能运行脚本的读者保留静态说明。实拍截图保留原格式；实际代码、终端命令和实测输出保留为可复制的文本。
- **文末速查**：全文完成后，再汇总本文用到的命令、关键参数、系统调用及必要的返回值说明；文件系统系列在速查之后加「名词解释」，用一句话说明本篇关键术语的含义。两个小节均沿用正文标题编号。
- **协作与发布**：每次完成一块，等作者校验后再写下一块。草稿默认 `draft: true`，只在明确要求发布时提交推送相关内容。发布前检查 Hugo 构建、图片、内部链接和实验可复现性。
- **换会话接续**：在草稿末尾用 Markdown 注释记录已写到哪里、哪些内容待校验与下一步；定稿后移除注释。规划与进度维护在《博客建设与写作计划》中。

## 一、内核源码篇的写法

### 1.1 从一个可以验证的问题出发

用一次对照实验提出问题，并写出读者可以核对的结果。例如，对同一路径 `open` 两次，两次读取都得到 `A`。一次 `open` 后再 `dup`，依次从两个描述符读取得到 `A`、`B`。接下来的源码要解释这两个结果，以及状态到底保存在哪个对象里。

### 1.2 先画对象关系，再跟调用路径

- **对象关系回答「状态在哪里」**。先用 SVG 标出索引、指针和共享边界，再摘出与实验相关的真实 C 定义，用 `/* … */` 标明省略字段。逐个解释字段由谁持有、何时变化、能否共享。例如 `fdtable.fd[]` 存放指向 `struct file` 的指针，`f_pos` 属于 `struct file`。用这两个字段解释为什么不同 fd 可以共享偏移。
- **调用路径回答「状态怎么变」**。从示例中的 C 接口和 strace 实际观察到的系统调用进入，沿当前调用场景追踪内核函数。每一步写清它对哪个对象做了什么，例如预留 fd、分配 `struct file`、关联路径和文件操作、安装 fd 指针。失败回滚、引用释放和间接调用分支在影响本节问题时展开。
- **在 VFS 边界交代分工**。顺着调用指出哪一步由描述符层组织，哪一步由 VFS 管理对象或分发，哪一步交给具体文件系统。讲到 `f_op` 之类的操作表时，交代函数指针从哪里来，以及当前调用在什么条件下走到哪个回调。

### 1.3 逐节核对观察结果和源码

- 源码链接固定到本文使用的 tag 或 commit。核对摘录字段、调用先后和条件分支。实验机器使用发行版内核、源码采用上游版本时，分别注明。
- 区分实验观察与源码解释。strace 可以证明调用及结果，内核内部的对象和先后顺序用源码说明。如果某个例子依赖特定文件类型或打开方式，在例子旁写清前提。
- 每块交给作者校验前，从结果倒查一次。读者能否指出状态存在哪个字段、由哪一步改变、为什么得到这个结果？缺了哪一步，就补对应的源码、图或实验说明。

## 二、概念篇的写法

- 名词与概念综述直接按定义、用途、相互关系和必要换算组织。具体数值用于解释概念，避免强行串联故事。机制与源码篇可选一个贯穿例子，保持地址、对象或输入的对应关系。
- 按「遇到什么问题 → 对象记录什么 → 操作后发生什么」引出术语。容易混淆的对象放进同一个例子里，说明它们各自控制哪一步，并用一个条件变化检验区别。
- 图展示可跟踪的关系或变化，例如同一组地址在写入前后怎样映射。正文至少带读者沿图走一遍。正文说完整段因果后，再用速查表收拢术语。
